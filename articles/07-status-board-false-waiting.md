# 看板说 40 张卡在等合入，其中 34 张的工作树早就没了：状态要从证据推导

结论先说：**多 Agent 的任务看板，每一行状态都要能回到一个结构化字段或一条外部证据；字段为空的时候，要去查证据，不能把“不知道”当成“没做”。** 我的看板脚本在四周里错了四次，每次错法不同，但都是这一条。第四次到今天还没修，下面的数字是今天上午现跑的。

背景：我用 Claude Code 拆任务和验收，用 Codex 实现。每张任务卡派出去之后，会留下一个证据目录：启动记录、事件流、Codex 的回执。一个只读脚本扫这些目录，打印一张表，告诉我每张卡现在在等谁：等 Codex、等验收、等我。它是我每天看“谁在等谁”的入口。

## 第一次：一张卡都没看到

10 月 26 日复盘，上一次复盘之后各项目会话自己派出了 13 个任务。脚本的输出里一个都没有。

原因是各会话留下的证据文件格式不一样：有的没有启动记录，有的事件流文件名不同。脚本只认一种写法，认不出来的就当不存在。

修法是按事件流文件发现任务，并在派发说明里写死证据文件的约定。这次的教训很朴素：**看板没显示，不等于没有活在跑。**

## 第二次：已经合入的卡显示“blocked”

10 月 31 日，看板上某个电商工具仓库有一张卡显示 blocked，像是在等第 2 轮。

实际情况：这张卡两天前就已经验收通过并合入了。回执里的 blocked 是沙箱临时目录的问题，验收方在沙箱外跑全量测试，2099 项通过。

脚本为什么看不到？两个原因：

1. 验收判决是一段自由文本，没有可以解析的字段；
2. 任务工作树合入后已经删除，脚本按工作树路径找卡，找不到。

也是在这一天，我把状态推导改成了现在的样子，借的是一个开源多 Agent 研究原型的规则：**一张卡只有一个阶段，由“它在等什么”决定；只读结构化字段，按顺序匹配，第一条命中就停；不从自由文本里猜。** 回执必须有 `status` 和 `human_action`，判决必须有 `verdict` 和 `final`。找不到卡的，单独标成“无法推导”，不混进“等验收”。

## 第三次：验收通过一周，还显示“等我回答”

11 月 13 日发现，有一张卡验收通过已经一周，看板上仍然是“等我回答”。

原因是匹配顺序。回执里的 `human_action` 写着一个问题，脚本先匹配到它，就停了。但那个问题任务会话早就答过，后面还写了 accept 判决。

修法：最新一轮的判决排在回执的 `human_action` 前面。两天后又补了一条：只有最新一轮的判决才决定谁在等，第 1 轮已经答过的 blocked 不能卡住第 2 轮。

“第一条命中就停”这条规则没错，但它把正确性全部压在了顺序上。**顺序要按“谁的证据更新”来排，不是按“谁更严重”来排。**

## 第四次：40 张“等合入”，今天还在

11 月 15 日盘点时，看板约 265 行，其中 39 行显示“已验收：等提交/PR/合入并归还工作树”，32 行在同一个数据平台仓库。抽查一张，任务分支早就合入了。

今天（11 月 19 日）上午我重跑了一遍，没改脚本：

- 一共 313 行任务；
- 40 行显示“已验收，等合入”，其中 34 行在那个数据平台仓库；
- 这 34 张卡的工作树目录，磁盘上一个都不在；
- 其中 9 张的任务分支还在，并且已经并入集成分支；另外 25 张连分支都删了，我抽查 7 张，6 张能在集成分支上找到对应的合入提交；
- 真正需要我决定的卡，只有 8 张。

也就是说，“等合入并归还工作树”这一栏里，至少 34 行对不上：工作树全都已经不在，其中 15 张我能直接证明已经合入。它们把 8 张真要我看的卡淹在了下面。

原因只有一行代码：

```python
returned = bool(worktree) and not os.path.isdir(worktree)
```

意思是：启动记录里有工作树路径，并且这个目录已经不在了，才算“已归还”。但这 34 张卡里有 33 张的启动记录根本没记工作树路径，字段是空的。空字段让整个表达式为假，于是脚本的结论是“还没归还”。

**字段为空，被当成了“否”。** 这和第二次是同一个错：缺证据的时候，脚本选了一个答案，而不是承认不知道，或者去别处找。

这一条的修法已经写进了 11 月 15 日的优化清单，还没合入。我先如实写在这里。

同一次运行里还有 16 行“执行中，无回执”，时长从 25 小时到 549 小时。脚本超过 6 小时就提示，但只提示，没有人去收。看板准不准是一回事，有没有人按它行动是另一回事。

## 可以拿走的做法

下面是简化版的阶段推导，加上第四次的修法（带注释的那一段是建议写法，我自己的脚本里还没合入）：

```python
def stage(n_runs, receipt, verdict, returned):
    """receipt: 最新回执的字段；verdict: (轮次, 结论, 是否终局)；每张卡只返回一个阶段。"""
    current = verdict if verdict and verdict[0] >= n_runs else None
    if current and current[1] == 'accept':
        return '已验收并归还' if returned else '等合入'
    if current and current[1] == 'blocked':
        return '等人回答'
    if current and current[1] == 'return':
        return '等人拆卡' if current[2] else '等派下一轮'
    if receipt is None:
        return '执行中'
    if receipt.get('human_action') not in (None, 'none', '无'):
        return '等人回答'
    return '等验收'


def is_returned(worktree_field, repo, task):
    # 字段有值：看目录还在不在
    if worktree_field:
        return not os.path.isdir(worktree_field)
    # 字段为空：不能直接算“否”，退到外部证据
    if os.path.isdir(os.path.join(repo, '.worktrees', task)):
        return False
    merged = subprocess.run(['git', '-C', repo, 'branch', '--merged', 'HEAD'],
                            capture_output=True, text=True).stdout
    return f'task/{task}' in merged.split()
```

照着做的时候注意四点：

1. **每个阶段写清楚它读的是哪个字段。** 回执和判决用固定字段，自由文本只给人看。脚本读不到字段，就标“无法推导”，单独列出来。
2. **匹配顺序按证据的新旧排。** 最新一轮的判决在前，旧回执里的问题在后。每次因为顺序出错，就把那张卡的名字写进注释，下次改顺序的人能看到。
3. **空值走另一条路。** 写每个布尔判断时问一句：这个字段为空时，表达式的结果是什么，这个结果对不对。我的四次错里有两次是这个。
4. **默认只显示要人动的行。** 今天 313 行里，有 238 行是各种“已结束”。它们应该只占一个计数，不占版面。

判断一张看板可不可信，可以抽一栏做一次对账：把这一栏里的每一行，拿到它描述的那个系统里核对一遍。我今天核的是“等合入”，40 行里至少 34 行对不上。对不上的比例这么高，说明这一栏在修好之前不应该拿来做决定。

这是系列第 7 篇。第 2 篇讲过钩子会冤枉执行方；这一篇是另一头：给人看的那张表，也会冤枉人。
