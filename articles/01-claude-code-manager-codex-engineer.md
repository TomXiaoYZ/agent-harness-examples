# 让 Claude Code 当经理、Codex 当工程师：152 张任务卡之后我学到的

我同时维护好几个个人仓库，包括一个数据平台、一个带实盘红线的量化研究仓库、几个电商工具，还有一个内容生产仓库。从 10 月 24 日起，我把分工固定成这样：

- **Claude Code 负责定义和验收**：想清楚要做什么、拆成任务、最后检查结果。
- **Codex 负责实现**：在给定的规格里写代码、跑测试。

从 10 月 28 日到今天，这套流程派出了 152 张任务卡，覆盖 7 个仓库。下面不讲工具怎么装，只讲四件让它从“偶尔能用”变成“每天在跑”的事，以及每件事背后那次具体的失败。

## 一、交接物不是聊天记录，是仓库里的一张卡

最早我在对话里直接跟 Codex 说要做什么，很快就出了问题。上下文散在聊天记录里，Codex 做完，我说不清它到底偏没偏题。

现在交接物只有一个：一个 Markdown 文件，放在目标仓库的 `docs/tasks/<日期>-<主题>/README.md`，提交到任务分支上。Codex 读的就是这份文件，我验收时对照的也是这份文件，提交记录可以证明两边看的是同一版。

卡里固定有这几节：

- 目标和用户路径
- 验收标准（必须是可执行的命令或可点开的页面）
- 边界（哪些文件、哪些系统不能碰）
- 授权（网络、可写目录、模型、推理强度）
- 必须通过的新测试
- 轮次记录

其中两节是踩过坑后加的。

**“授权”节是唯一的参数来源。** 派发脚本只从卡里读网络开关和可写目录，命令行参数想放宽就会被拒绝。要放宽，就开一张新卡。这样每次越权都留有痕迹，不会因为某次手动加了个参数就悄悄变成常态。

**“必须通过的新测试”由我先写好，Codex 必须先让它们失败再去实现。** 这条规则的目的是防止 Codex 多做：测试覆盖不到的行为，它不该去实现。

## 二、卡有大小上限，并且最多两轮

早期有一张卡写到了 700 行，涉及 4 个文件。Codex 照做了，但我验收时自己也读不完。还有一张交接卡，第一轮因为工作树放在仓库内的 `.codex/` 目录下，沙箱拒绝写入，回执报 `blocked`。第二轮写出了文档，又在 `git add` 时被拒绝，因为链接工作树的 `.git/` 对它是只读的。

这两次 Codex 都没有乱来：它停下来，如实报了 `blocked`，主检出一个字节都没动。但这也说明问题出在卡和环境上，不在执行者身上。

于是加了两条硬限制：

1. **卡不超过 12 KB，不贴源码。** 源码只写路径和符号，让 Codex 自己去工作树里读。派发前用一个自检脚本检查大小、有没有贴代码、有没有缺小节、有没有残留占位符，不通过就不派。
2. **最多两轮。** 第二轮还被退回，就不派第三轮，要么把卡拆小，要么带着证据交给我决定。

效果可以用数字看。152 张卡里：

- 116 张一轮结束，占 76%；
- 29 张用了两轮；
- 用了三到四轮的有 7 张：
  - 1 张是定下两轮上限之前的旧卡；
  - 2 张涉及浏览器或音视频操作；
  - 另外 4 张是在规则定下之后照样超了轮数。

最后这 4 张说明，“最多两轮”这条规矩最终还是靠人来执行。汇总脚本能把超过两轮的卡标红，但拦不住人再派一轮。

浏览器那 2 张也给了一条规则：**脚本派出的 Codex 线程拿不到浏览器插件的凭据**，所以打开网页、截图、登录这类步骤一律不派给它，改成由我这边的 Claude 在验收时做。有一张卡就因为这个原因跑了四轮，每一轮都卡在“浏览器访问宿主不可用”。

## 三、经理比工程师贵 41 倍

这是我最没想到的一个数字。

在能同时算出两边用量的 141 张卡上，Claude Code 一侧的 token 中位数是 25.5M（输入加缓存），Codex 一侧是 0.8M。两者之比的中位数是 41 倍，最高的一张是 363 倍。

需要说明：Claude Code 这一侧大部分是缓存读取，单价比新输入低很多，所以 41 倍是 token 量的比，不是账单的比。但趋势很清楚：真正花钱的不是写代码的那一方，而是负责规划和验收、上下文越积越长的那一方。

原因在于每次请求都会把整段对话重新发送一遍。我一开始是一个项目一条长会话，规划、派发、验收全在里面，其中一条会话的转录文件有 32 MB。做到后面的卡时，每一轮都在重新读前面所有卡的历史。

改法是**一张卡一条任务会话**：

- **项目会话只做规划和拆卡。** 每张卡的派发、监控和验收在一条新开的会话里完成，结束时只交回 30 行以内的判决。
- **判决写回卡的“轮次”节，不靠对话历史。** 项目会话随时可以清空，不会丢状态。
- **验收分两个阶段。** 先只看卡，写出检查清单；再看 diff，逐条对照。这样就不会被 Codex 的自我总结带偏。

改完之后比值仍然偏高，我还在追。现在派发汇总脚本会自动标出“CC 侧超过 Codex 5 倍”的卡，让我回头检查项目会话是不是又在自己读日志、跑构建。

## 四、审计会误伤，所以审计本身也要验收

为了不让超预算和多余的防御性代码拖到下一轮才被发现，我给 Codex 线程加了一个回合结束时的自检钩子。每个回合结束，它都会对 diff 跑一遍审计，不通过就退回让 Codex 在同一回合里改，最多退回两次。

结果这个钩子自己成了阻塞来源。最近的汇总里，好几张卡被卡住的原因是“审计把测试函数名当成了文件路径”，或者“测试行数超过源码的 1.5 倍，但任务卡里没写这个限制”。Codex 在回执里把这些都如实写了出来。

我从中得到的教训是：**门禁也是代码，也会有 bug。** 现在每次复盘，我会单独把“被审计误判的阻塞”挑出来，先修审计，再看是不是 Codex 的问题。

## 可以直接拿走的部分

任务卡模板、卡的自检脚本思路、两阶段验收清单，我整理成了一个去敏的示例仓库：https://github.com/TomXiaoYZ/agent-harness-examples。三条最值得先抄的：

1. 交接物放在仓库里，提交到分支，不要靠聊天。
2. 卡有大小上限，最多两轮，第二轮不过就拆卡或升级给人。
3. 计算“每个被接受的改动花了多少”，而不是看总用量。真正贵的往往是经理那一方。
