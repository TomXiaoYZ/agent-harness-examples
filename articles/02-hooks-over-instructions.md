# 写进说明的规则会被忘，写进钩子的不会：但钩子也会冤枉人

上一篇讲了任务卡和“最多两轮”。这一篇讲另一半：规则写好了，怎么保证 Agent 真的照做。

## 一段 400 字的禁令，挂在每一轮对话里

一开始，我把双 Agent 的分工写进全局说明文件，是一段 400 多字的禁令：Claude Code 不改代码，Codex 不改目标，不碰生产配置……每个会话的每一轮都会带上这段话。

规则照样被违反。10 月 29 日我翻了一遍转录：在一个数据平台仓库里，Claude Code 自己做了 111 次代码编辑，大部分是它分内的设计原型，但约 20 次是验收时在任务工作树里“顺手改一下”代码，越界了。Codex 那边的问题是防御性代码多，而且要等我验收时才发现，于是又多跑一轮。

Claude Code 官方最佳实践里有一句话说得很准，大意是：如果你一直给 CLAUDE.md 的某一行加重点，Claude 还是会漏掉，那这一行就该改成钩子（[原文](https://code.claude.com/docs/en/best-practices)）。

后来我把那段规则从 400 多字压到 4 行，细则放进技能文件，真正必须遵守的部分交给钩子。

## 三个钩子，各管一件事

**1. Claude Code 侧：编辑前拦截（PreToolUse，10 月 29 日上线）**

只要编辑目标是“实现已交给 Codex 的仓库里的代码文件”，钩子就直接拒绝，提示把这处改动写进任务卡的下一轮。文档、任务卡、原型、Agent 配置放行；Claude Code 自己负责开发的仓库整体放行。

上线当天我在一个正在运行的会话里试着写一个代码文件，被当场拒绝，文件没有创建。这说明它不用重启会话就生效。

**2. Claude Code 侧：命令前检查环境（PreToolUse，Bash，11 月 10 日上线）**

这个钩子拦两类命令：手敲的 `git worktree add`（要求改用会登记账本、有数量上限的建树脚本），以及没带任务标签的后台容器、没带项目名的 `docker compose up`。没有身份标记的环境，事后没人能收。原因在第 4 篇细讲：环境是借的。

**3. Codex 侧：回合结束前自检（Stop，10 月 30 日上线）**

Codex 每个回合结束前，钩子对改动跑一遍审计，查三类问题：超出预算、动了卡外的文件、加了卡里没有依据的防御性代码。不通过就把审计结果退回给 Codex，让它在同一个回合里改。

这里有两个设计决定：
- **最多退回 2 次。** 还有分歧就放行，让 Codex 在回执里如实列出没处理的项。否则会变成死循环。
- **只审计派发脚本登记过的线程。** 我自己平时开的 Codex 会话不受影响。

这个钩子的思路来自一份实践总结里的观察：一次审计里，发布门禁的 10 个输入有 4 个是被检查组件自己的报告，等于让 Agent 给自己打分；门禁应该接外部证据（[解读文章](https://codex.danielvaughan.com/2026/08/19/engineering-reliable-coding-agents-system-around-model-codex-cli-harness-dependency-chain-gated-practices/)）。Codex 说“测试通过”只是一个声明，审计跑出来的结果才算证据。

## 第一个坑：钩子根本没跑，而我差点以为它通过了

上线当天做探针：让 Codex 故意写一段带 `try/except Exception: pass` 的代码，然后结束回合。结果钩子没有拦，登记文件里的退回次数还是 0。

直接用同一个线程 id 手动调用钩子脚本，它正确地拦下并报出 3 处命中。脚本没问题，那就是 Codex 根本没调用它。可当时没有任何办法区分“没跑”和“跑了没过”。

于是我在钩子最前面加了一行日志：每次被调用就记下线程 id 和事件。再测一次，日志是空的，证实 Codex 没调用。原因是这个钩子还没被标记为“受信任”，Codex 只运行受信任的钩子。补上信任项后第三次探针端到端通过：第一次 Stop 被拦，Codex 在同一回合删掉 `try/except`，第二次 Stop 放行。

## 第二个坑：钩子冤枉了不少人

到 11 月 15 日，我做了一次盘点：

- 一共 117 条登记过的 Codex 线程，钩子日志里有 538 次调用（含未登记线程的放行记录）。
- **其中 87 条线程，钩子把 2 次退回额度用满了，约占 74%。**

我第一反应是 Codex 太不听话。按回执里写的阻塞原因逐条归类，46 个任务的阻塞跟审计有关，大致是：

- 约 11 个：测试行数超过源码 1.5 倍被退回，但有的任务卡本来就写明了测试要写多少；
- 约 8 个：卡在“必须通过的新测试”里点名的测试文件，因为没在“改动预算”里重复写一遍，被判成“清单外文件”；
- 约 8 个：卡里写的测试路径和仓库里的实际路径对不上，审计就判“必需测试缺失”；
- 约 13 个：防御性代码命中。其中有的并不吞异常，比如两个 `try/finally` 只用来做数据库回滚和关闭连接。

前三类加起来，比真正的防御性代码问题还多，而且错在审计和卡的写法，不在 Codex。

更早的一次（11 月 5 日），同一张卡被退回两次，Codex 在回执里一条条写明：“审计将三个已存在且通过的测试函数名误识别为缺失文件”，测试新增 30 行超出钩子按比例算出的 6 行限制，“任务卡未列该限制”。在这些卡上，它没有为了过审去删掉卡里要求的测试或必要的回滚代码，而是把冲突写进回执交给我判断。

同一张回执里还有第三条阻塞：一个测试需要绑定本地端口，被沙箱拒绝。这一条不怪审计，也不怪 Codex，是卡把需要端口的测试放进了 Codex 的验收命令。之后卡模板加了一句：需要端口、网络或外部服务的测试，不放进 Codex 的测试命令，由验收方在沙箱外跑。

## 由此定下的三条规则

1. **门禁也是代码，也要验收。** 复盘时把“审计误判导致的阻塞”单独列出来，先修审计，再判断是不是执行方的问题。11 月 5 日和 15 日各修过一轮审计脚本。
2. **卡和审计冲突时，以卡为准。** 卡写了测试预算，就按卡的预算校验，不再套默认的 1.5 倍；卡里点名的测试文件自动算进允许改动的清单。审计规则和卡模板要一起改。
3. **钩子要能区分“没跑”和“跑了没过”。** 每次调用都记一行日志。否则钩子静默失效时，你会以为一切正常。

还有两件事没做完：钩子目前不记录每次拦截的原因，上面的归类只能从回执里反推；防御性代码命中要不要继续在回合内强制修，还没定。

## 什么该进钩子，什么留在说明里

我现在的分法：
- **进钩子**：违反后代价高、可以机械判断的规则。比如不改已委派仓库的代码、容器必须带标签、改动超出预算。
- **留在说明里**：需要判断力的东西。比如“先确认谁用、希望什么改变、怎样算完成”。
- **两样都不要**：只是偏好的东西。

最后提醒一个容易忽略的点：这几个钩子的内部错误一律放行（exit 0）。钩子自己出 bug 时宁可漏拦，也不能把正常工作全部卡死。

示例仓库（https://github.com/TomXiaoYZ/agent-harness-examples）里目前有任务卡模板和卡自检脚本的通用版本。

**统计口径**

- 钩子上线时间：Claude Code 编辑拦截 2026-10-29，Codex 回合末自检 2026-10-30，环境检查 2026-11-10。
- 盘点时间：2026-11-15 21:12（美东），数字来自当时的一次只读盘点，之后会随新派发变化。
- “登记线程”指派发脚本写入登记文件的 Codex 线程，共 117 条；退回次数为 2 的 87 条，为 1 的 9 条，为 0 的 21 条。
- “调用次数”取自钩子日志的行数，每次调用记 1 行，包含未登记线程。
- 阻塞原因归类：按回执中写明的阻塞原因人工归类，数字为约数；钩子本身不记录拦截原因。
- 10 月 29 日的编辑次数来自当日对一个仓库 Claude Code 转录的统计。
