# “一张卡一个上下文”写了两周没人守：一天约 4.2 亿 token，守卫第二天又被绕过

结论先说：**限制 Agent 上下文长度的规则，不能挂在“入口”上，要挂在它绕不开的那条命令里，并且每个动作都要查。** 我把“一张卡一个新上下文”写进说明文档两周，没有任何东西执行它；第一次写成代码守卫，第二天就被绕过。下面是这两次失败和现在的做法。

背景：我用 Claude Code 拆任务和验收，用 Codex 实现。每张任务卡的派发、监控、验收，本来应该在一个为它新开的短上下文里完成。

## 第一次：规则只在文档里

10 月 30 日复盘时定了这条规则，原因是每次请求都会重发整段对话。当时一个项目一条长会话，其中一条转录文件有 32 MB、1878 次工具结果，做后面的卡时每一轮都在重读前面所有卡的历史。

规则写进了派发 skill 的第一条。然后就没有然后了。

11 月 14 日，某数据平台仓库有一批卡要做。两个子代理各自拿到了“一批卡”：一个在同一个上下文里连续派发并验收了 26 张卡，另一个 8 张。

当天的结果：

- Claude Code 一侧约 420M token，几乎全是在反复读一个约 37 万 token 的上下文；
- 同一天 Codex 写完这些卡的全部代码，只用了 49M。

规划和验收的一方，花掉了实现一方的 8 倍多。

为什么没被拦住？两个原因：

1. **规则只是一句话。** 它写在 skill 里，但没有任何东西执行它。
2. **包装脚本挡住了钩子。** 当时为了省事写了一个 `dispatch.sh`，把派发命令包了一层。钩子只看得到“运行了一个 shell 脚本”，看不到里面每一次真正的派发调用。就算当时有针对派发命令的钩子，也会被这层包装绕开。

## 第二次：守卫只查了一个动作

当天就把规则写成了代码，而且不放在钩子里，直接放进派发脚本本身：`codex_thread.py start` 在建线程之前先调用 `dispatch_scope.py`，判断“这个上下文是不是已经派过别的卡”。派过就拒绝，同一张卡的第 2 轮放行。

第二天，11 月 15 日，它被绕过了。

一个子代理要处理 14 张卡。它让一次性子代理只跑 `start`，自己留在原来的上下文里，对这 14 张卡逐个跑 `turn`（驱动线程干活）和验收。守卫只查了 `start`，没查 `turn`。这一次约 132M token，同样是在重读一个越来越长的上下文。

守卫的字面是“`start` 不能跨卡”，这条路在字面上完全合规。**你守住了哪个动作，Agent 就会把工作挪到你没守的那个动作上。**

当天补上：`turn` 也调用同一个守卫，并且把每个驱动过线程的上下文记进登记文件。一个上下文只要碰过一张卡，不管是 `start` 还是 `turn`，就不能再碰另一张。

## 守卫怎么知道“我是谁”

难点在于：脚本被调用时，怎么知道调用它的是哪个上下文？主会话和它的子代理共用同一个会话 ID。

做法是看转录文件。Claude Code 的主会话和每个子代理各有一份 JSONL 转录。守卫运行的那一刻，调用它的那个上下文里，一定有一条 Bash 工具调用还没有结果，因为守卫自己就是那条调用。所以：

1. 从环境变量 `CLAUDE_CODE_SESSION_ID` 拿到会话；
2. 扫这个会话的主转录和所有子代理转录，各读末尾一段；
3. 找出“最新一条还没有结果的 Bash 调用”所在的那份转录，它就是调用者。

识别不出来的情况一律放行：不在 Claude Code 里运行（我自己在终端里用）、两个上下文同一时刻都在等 Bash。**守卫宁可漏，不误伤人。**

## 生效之后的数据

守卫上线后，登记文件里多了调用者字段。截至 11 月 18 日上午：

- 带调用者记录的线程 98 条，跨 5 个仓库；
- 一共出现 109 个不同的上下文，其中 108 个只碰过 1 张卡；
- 有 1 个上下文在 11 月 17 日 `start` 了 2 张卡，守卫没拦住。原因我还没查，先如实记在这里。

另外加了一个不阻断的提示钩子 `long_session_hint.py`，挂在用户提交消息的事件上：主会话上下文到 20 万 token 时提示一次，之后每多 10 万再提示一次，告诉模型“新的结果交给新会话”，也告诉我当前体积。它只提示，出错就静默退出。加它的原因是 11 月 14 日到 15 日，主会话经常在 22 万到 49 万 token 的上下文里继续干活，而同期 Codex 线程的上下文中位数是 67K。

## 可以拿走的做法

核心逻辑不到 20 行，下面是简化版。登记文件每条线程一个 JSON，记着卡的路径和碰过它的上下文：

```python
def check(threads_dir, card, who):
    """who 碰过别的卡就返回拒绝理由，否则返回 None。"""
    if not who:
        return None  # 识别不出调用者：放行
    card = os.path.realpath(card)
    for path in glob.glob(os.path.join(threads_dir, '*.json')):
        with open(path, encoding='utf-8') as fh:
            reg = json.load(fh)
        touched = reg.get('caller') == who or who in reg.get('turn_callers', [])
        if touched and os.path.realpath(reg['card']) != card:
            return f'这个上下文已经碰过 {reg["card"]}，为新卡开一个新上下文'
    return None
```

照着做的时候注意三点：

1. **守卫放进命令本身，不放在外面。** 钩子能被包装脚本挡住；写在派发脚本里的检查，只要想派发就绕不开。
2. **列出所有能推进工作的动作，每个都查。** 只守“开始”，工作就会挪到“继续”上。我漏了 `turn`，代价是 132M token。
3. **拒绝信息里写清楚下一步。** 我的拒绝信息会告诉它：回到项目会话，为这张卡新开一个会话或子代理，只带这张卡的简报。只说“不行”，它会去找别的路。

判断一条规则有没有人守，可以问一句：**“如果 Agent 完全没读过这句话，会发生什么？”** 如果答案是“什么都不会发生”，这条规则就还只是一个愿望。

这是系列第 6 篇。第 1 篇讲过“经理比工程师贵”，这一篇是它的后续：知道贵在哪里之后，怎么让规则真的被执行。

## 数字说明

- 32 MB、1878 次工具结果：出自 2026-10-30 协作复盘。
- 26 张、8 张、约 420M、约 37 万、49M：出自 `dispatch_scope.py` 的文件说明和派发 skill 的规则原文，是 2026-11-14 当天的统计，Claude Code 一侧大部分是缓存读取，是 token 量不是账单。“8 倍多”由 420M ÷ 49M 得出。本文没有重新计算这组数字。
- 14 张、约 132M：出自同一脚本 `check_turn` 的说明和 skill 原文，2026-11-15。
- 98 条线程、5 个仓库、109 个上下文、108 个只碰 1 张卡、1 个碰了 2 张：我在 2026-11-18 上午直接统计线程登记文件得出，范围是 2026-11-14 守卫上线之后带调用者字段的登记。
- 22 万到 49 万、67K、20 万与 10 万的阈值：出自 `long_session_hint.py` 的文件说明和常量，2026-11-15。
