# Codex 派出去的线程，为什么在 App 侧栏里找不到：7 根探针的实测

前两篇讲了任务卡和钩子。这一篇讲一个更早遇到的问题：Claude Code 派活给 Codex 之后，我想在 Codex App 里点开线程看过程，必要时自己接管。前提是线程得出现在 App 侧栏对应的项目文件夹里。这比想象中难。

下面的结论都来自 2026 年 10 月 24 日的实测，当时 App 自带的 Codex CLI 是 0.164.0。Codex App 迭代很快，细节以你手上的版本为准。

## 现象：1067 条 exec 线程，App 界面里一条都没有

最省事的派活方式是 `codex exec`：非交互运行，输出 JSONL 事件流，最后一条消息可以写进文件。

问题是 App 里找不到这些线程。查本机的 Codex 状态库，exec 来源的线程都在，一共 1067 条；但 App 的 `thread/list` 默认不含 exec 来源，要显式传 `sourceKinds=["exec"]` 才查得到。这 1067 条在 App 的界面状态里出现 0 次。

对照组是另一套工具经 App 自带的守护进程（app-server）建的 47 条线程，App 正常显示。

**结论一：要让 App 看得见，就通过 App 自己的守护进程建线程。** exec 只留给不需要人看的一次性只读查询，真要看可以在终端用 `codex resume <id>` 打开。

## 7 根探针

通过守护进程建线程，要传 `cwd`、`projectId`、`threadSource` 等参数。`projectId` 在生成的 schema 里没列，但服务端接受。到底哪个参数决定线程进不进项目文件夹？我建了 7 条只读探针线程（A–G），每条换一种参数组合，再截图核对侧栏。

| 探针 | 条件 | 结果 |
|---|---|---|
| A | `threadSource` 为空 | 首次刷新时没出现，后来才出现 |
| B | 带 `projectId`，cwd 是工作树子目录 | 只出现在 Recents，不进项目文件夹 |
| E | 不带 `projectId`，cwd 等于仓库根 | 照样出现在项目文件夹里 |
| G | 建好后用 `turn/start` 的 cwd 覆盖到工作树 | 线程存储的 cwd 被改写，掉出项目文件夹 |
| 其余 | 不同 `threadSource` 与客户端名的组合 | `agent_created_thread` 和 `user` 都可见；客户端名不影响显示 |

得出的规则：

1. **进项目文件夹的条件，是线程 cwd 恰好等于该项目的某个根路径。** 跟 `projectId` 无关。
2. **`threadSource` 不要留空。**
3. **不要用 `turn/start` 的 cwd 覆盖。** 它会改写线程存储的 cwd，线程立刻掉出项目。所以“线程挂在仓库根、命令跑在工作树里”这条路走不通。

还有一条路我没走：项目的根路径列表可以改，把任务工作树加进去，它也能进文件夹。但这会污染自己在 App 里维护的项目列表，不作默认。

## 那工作树放哪里？

线程 cwd 必须是仓库根，每个任务又要在独立工作树里干活。最后的方案：

- 工作树放在 `<repo>/.worktrees/<task>`，位于线程 cwd 之下，`workspace-write` 沙箱天然允许写入，不用额外配置可写目录。
- 回合指令写明“所有读写和 git 操作都在这个工作树内进行”。代价是 Codex 理论上也能写主检出，所以验收时要核对主检出没被动过。
- **不要放在 `<repo>/.codex/` 下。** 第一次派“项目交接”任务时，工作树就放在那里，Codex 收齐了证据，写文档时被沙箱拒绝，回执如实报 `blocked`。
- 挪到 `.worktrees/` 后的第二轮，文档写出来了，`git add` 又被拒：链接工作树的 git 元数据在主仓库的 `.git/worktrees/` 下，沙箱把 `.git/` 也当只读。所以 **Codex 改文件，Claude Code 验收后再提交。** 这条后来成了固定分工。

两轮里 Codex 都是遇阻就停下、如实写回执，没有绕路，这也顺带验证了回执格式。

## 两个坑

- **App 不会实时感知外部建的线程。** 新线程和归档一般几分钟内才出现在侧栏。我试过用 `codex app <仓库根>` 切项目来催刷新，两次切换后截图都还是旧列表。所以验收不能拿“侧栏马上出现”当标准。
- **别去改 App 的界面状态文件。** App 在本机有一份界面状态的落盘文件，里面也记着线程归哪个项目。它是 App 进程内存的副本，外部改写会被覆盖，甚至损坏状态。当时线程归属正从这份客户端文件迁往服务端的项目表，外部客户端只走服务端那套接口（`project/list` 取项目和根路径，`thread/start` 建线程）。

## 可以拿走的东西

- 要人能看见、能接管，就走 App 的守护进程，不用 exec。
- 线程 cwd 等于项目根；工作树放在 `.worktrees/` 下；不用 cwd 覆盖。
- 协议以 App 自带二进制 `codex app-server generate-json-schema` 生成的 schema 为准，不抄网上的文档。

一个后续变化：App 26.1103 版起，守护进程不再随 App 常驻。我的派发脚本发现控制 socket 不在时，会先用 `codex app-server daemon start` 拉起它，拉不起来就停下报错，不悄悄退回 exec。

示例仓库（https://github.com/TomXiaoYZ/agent-harness-examples）目前只有任务卡模板和卡自检脚本，派发客户端没有放进去。
