# 提醒钩子装上之后，单次调用的上下文还是涨到 69 万：上限要写进默认值，不能只靠提示

结论先说：**想限制 Agent 的上下文，提示它“该收口了”不够，要把上限改成宿主的默认值。** 我装了一个长会话提示钩子，装上后的第一个整天，单次调用的上下文最大还是有 68.9 万 token。后来改了两行配置，之后三天，单次调用的上下文一次都没超过 17.1 万。

背景：我用 Claude Code 拆任务、做验收，用 Codex 写代码。第 6 篇讲过，规划和验收这一方的 token 消耗，常常是写代码那一方的好几倍。原因不是活多，而是每次调用都要把整段上下文重新读一遍。

## 第一次：只装了提示

11 月 15 日，我加了一个提示钩子 `long_session_hint.py`，挂在“用户提交消息”这个事件上。主会话的上下文到 20 万 token 时提示一次，之后每多 10 万再提示一次，内容是：“新的结果请交给新会话。”它不拦消息，出错就静默退出。

11 月 16 日是钩子上线后的第一个整天。我从本机日志里统计了这一天：

- 4688 次调用，合计约 6.62 亿 token；
- 单次调用上下文的 p90 是 28.9 万，最大是 68.9 万；
- 子代理占全部用量的 56%，其中 96% 跑的是 Opus。

按设计，这一天里上下文超过 20 万的会话都该收到提示，但上下文照样涨到了 68.9 万。原因不难想：模型看到提示的时候，手上正在做的事还没做完，“先做完这一步”永远是对的；而这个钩子只看主会话，子代理不经过它，在主会话之外自己涨。

**提示只能改变“知道”，改变不了“做”。**

## 复盘：钱花在哪

11 月 17 日，我把近 8 天的用量摊开来看，原因有三条：

1. **上下文不压缩。** 会话开的是 1M 窗口，要快到 1M 才会自动压缩。近 7 天单次调用上下文的中位数是 13.6 万，p90 是 38.9 万，最长的一个会话连续开了 136 小时。
2. **子代理全跑 Opus。** 子代理约占全部用量的一半，几乎都是新开上下文的通用子代理，没有指定模型，默认就是 Opus。用量最大的一个会话派出了 71 个。
3. **固定开销高。** 每个会话的第一次调用就带着约 6.7 万 token：系统提示、工具定义、技能列表。其中有几个插件我平时根本用不到。

## 第二次：改默认值

当天改了三处，全部写在 `~/.claude/settings.json`，只对新开的会话生效：

```json
{
  "env": {
    "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "200000",
    "CLAUDE_CODE_SUBAGENT_MODEL": "sonnet"
  },
  "enabledPlugins": {
    "some-unused-plugin@marketplace": false
  }
}
```

- 主会话上下文到 20 万左右就自动压缩；
- 子代理默认用 Sonnet，明确指定了模型的子代理不受影响；
- 关掉三个用不到的插件。

提示钩子留着。它现在的作用是告诉我会话已经长了，而不是指望模型自己停下来。

## 之后三天

今天（11 月 21 日）凌晨，我用同一个脚本、同一种去重口径重算了一遍。先核对：11 月 10 日到 16 日每天的调用次数和合计，和 17 日复盘表里的数字逐日一致。然后看改动之后：

| 日期 | 调用次数 | 合计 | 上下文 p90 | 上下文最大 | 子代理占比 | 子代理里 Opus 占比 |
|---|---|---|---|---|---|---|
| 11-16（只有提示） | 4688 | 6.62 亿 | 28.9 万 | 68.9 万 | 56% | 96% |
| 11-18 | 3998 | 5.30 亿 | 16.1 万 | 17.1 万 | 9% | 13% |
| 11-20 | 1875 | 1.97 亿 | 15.5 万 | 17.0 万 | 29% | 8% |

最确定的变化是上限：改动之后，单次调用上下文最大 17.1 万，p90 稳定在 16 万上下。这正是压缩窗口该起的作用。子代理里 Opus 的比例从九成以上降到一成左右。

两件事要说清楚：

- **每天的合计不能直接比。** 每天干的活不一样，11-20 少，主要是因为那天活少。我只拿“单次调用”的形状来比，不拿总量算节省了多少钱。
- **固定开销没怎么降。** 我按“每个会话的第一次主调用”统计：改动前中位数约 7.9 万，改动后约 6.9 万，只降了一成多。关掉的插件只占固定开销的一小块，这一项还没解决。

正式复测定在 11 月 24 日，到时看满一周的数据。

## 可以拿走的做法

1. **先量再改。** 按 `message.id + requestId` 去重，按天汇总，记下单次调用上下文的 p50、p90、最大值，以及子代理占比。没有基线，改完就说不清有没有用。
2. **上限写进默认值。** 压缩窗口和子代理模型都是宿主的配置项，写进去以后，模型想不想收口都不影响它。提示钩子可以留着给人看。
3. **子代理单独看。** 主会话上的钩子管不到子代理。子代理的模型、上下文要单独统计、单独设默认值。
4. **只比形状，不比总量。** 每天的活不一样，总量涨跌说明不了什么。上下文 p90、最大值、模型占比，这些是“每次调用长什么样”，才能拿来对比。
5. **写清代价和回退。** 压缩会丢细节；子代理做复杂审查时质量可能下降，这类任务可以单独指定 Opus。回退办法是删掉那两行 env。

统计脚本的核心只有几行：

```python
seen = set()
for line in open(transcript):
    rec = json.loads(line)
    msg = rec.get('message') or {}
    usage = msg.get('usage')
    if not usage or (msg.get('id'), rec.get('requestId')) in seen:
        continue
    seen.add((msg.get('id'), rec.get('requestId')))
    ctx = sum(usage.get(k) or 0 for k in
              ('input_tokens', 'cache_creation_input_tokens', 'cache_read_input_tokens'))
    # 按日期、是否子代理、模型累加 ctx 和 output_tokens
```

这是系列第 8 篇。第 6 篇说守卫要挂在 Agent 绕不开的命令里；这一篇是同一件事的另一面：上限要放在 Agent 不用“想”的地方。

## 数字说明

- 提示钩子的阈值（20 万，之后每 10 万）、只提示不阻断：出自 `long_session_hint.py` 的文件说明和常量；上线时间按提交记录，是 2026-11-15 上午。
- 近 7 天上下文中位数 13.6 万、p90 38.9 万、136 小时、子代理约占一半、71 个子代理、首调用约 6.7 万、三处配置改动及其代价：出自 2026-11-17 的 Claude Code 用量复盘。
- 表格里的数字，以及 11-16 的 56% 和 96%：我在 2026-11-21 凌晨只读扫描本机 Claude Code 日志得出，按 `message.id + requestId` 去重、按美东时间分天，“合计”是输入、缓存写入、缓存读入、输出之和。这是本机日志，不是账单。11-10 到 11-16 的调用次数和合计与复盘表逐日一致。
- 首调用 7.9 万与 6.9 万：同一天按“每个主会话第一条带用量的记录”统计，改动前取 11-10 到 11-16 共 50 个会话，改动后取 11-18 以后共 38 个会话。它和复盘里的 6.7 万统计窗口不同，所以没有拿来互相比较。
- 配置读回：2026-11-21 读 `~/.claude/settings.json`，两项 env 分别是 200000 和 sonnet。
- 11-19 那一天日志里只有 336 次调用，比前后几天少很多，原因没查，所以没有放进表里。
