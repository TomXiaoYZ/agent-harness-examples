# 规则文件设了 10 KB 上限，不到三天只剩 16 字节：清理时又翻出 4 处互相矛盾

结论先说：**“再加规则就得先删”写在注释里，等于没写。** 11 月 20 日，我给 Agent 的全局规则文件加了一条测试：不超过 10,000 字节，当时它是 9,111 字节，注释里写着“再加规则就得先删”。不到三天，4 次提交各加了一点，一条都没删，文件涨到 9,984 字节，离上限只剩 16 字节。测试一直是绿的。11 月 22 日晚上做了一轮清理，压到 7,186 字节，上限收到 8,000，顺手查出 4 处规则互相矛盾，其中一处是我前一天的修复自己加进去的。

背景：这个规则文件是 Claude Code 和 Codex 每个会话开头都会整份加载的那份“全局约定”。第 9 篇讲 CI 修绿时提过它：上游模板的上限是 4,000 字节，我放宽到 10 KB，承认“瘦身这件事没做，只是把天花板定在了现状上面一点”。这一篇就是那块天花板后来的样子。

## 发生了什么

设上限之后，改过这个文件的提交一共 4 次：

| 时间（美东） | 改了什么 | 大小 | 距上限 |
|---|---|---|---|
| 11-20 22:25 | 加一个新的子 agent 类型 | 9,120 | 880 |
| 11-21 03:26 | 前端改动必须走一套验收技能 | 9,407 | 593 |
| 11-22 00:28 | 母会话不空等（第 10 篇那次修复） | 9,850 | 150 |
| 11-22 21:18 | 再接入一个 agent，各 agent 共用项目记忆 | 9,984 | 16 |

每一次单独看都有道理，都是当天真实问题的结论。但 4 次提交的改动加起来是“新增 5 行、删 3 行”，删掉的 3 行都是被改写的旧句子，不是被腾出来的位置。没有一次真的“先删再加”。

真正的问题是 11 月 22 日晚上做清理时才看到的。我让 Agent 审一遍整套规则，找冲突、重复、过时的描述，它报回来：

- **4 处冲突。** 最典型的一处：全局规则里写着“要在终端里可见的活用派发脚本，不拿内置子代理顶替”，派发技能第 4 步写的却是“每张卡开一个新的子代理做验收”。前一句是第 10 篇那次修复加进去的，我当时只想着“别让母会话空等”，没去翻技能里怎么写。另外三处：一处说“交付后自主续接下一项”，另一处说“只有我明确要求才启动其他会话”；模型默认值没写清是给谁的；派发对象列表里写了一种 agent，却没有对应的模板。
- **3 处文档和现状不符。** 说明文件写预算是 4,000 字节，测试实际是 10,000；写默认 17 个技能，清单里实际是 24 个；写某个定时检查“已安装”，其实没装。
- **13 处“（人名，日期）”式标注。** 每条规则后面都挂着是谁、哪天定的，有的还带一段复盘故事。这些对 Agent 执行没有用，每个会话却都要读一遍。

## 为什么会这样

三层原因。

**第一层：测试只管上限，不管趋势。** 测试断言的是“≤ 10,000”。9,984 也是绿的。注释里那句“先删再加”，没有任何东西去检查。

**第二层：新规则总是“挂”在最相关的那一条后面。** 4 次提交都是在已有条目后面接一句，行数几乎不变，每行越来越长。这样写最省事，也最不容易被人注意到：看 diff 只是改了一行。

**第三层：同一件事写在两个地方。** 卡的大小上限、轮次、环境归还这些细节，全局规则里写一遍，派发技能里又写一遍。改了一边，另一边就过时；加一条新规则时，也只会去看自己正在改的那个文件。冲突就是这么来的：不是谁写错了，是两处各自是对的，放在一起就打架。

## 修法：一个提交

11 月 22 日 21:35 的清理提交做了四件事：

1. **重写成 5 节**（分工与沟通、项目会话与派发、事实与工作区、质量、必须保留的边界），9,984 字节降到 7,186 字节，按字符数是 4,962 降到 3,566。
2. **上限从 10,000 收到 8,000 字节**，注释改成“再加规则先删旧的”。
3. **4 处冲突各写一个结论。** 比如子代理那条：只有为了隔离上下文的 Claude Code 任务会话可以用内置子代理，其余派发走派发脚本。续接那条：同一目标内已授权的下一步可以续，开新会话、派新卡要我要求或仓库的续接模式允许。
4. **细节只留一处。** 卡、轮次、环境归还的细节只留在派发技能里，全局规则只写一句“见某技能”。13 处人名日期标注全部去掉，出处留在 git 历史里。3 处过时描述改成和现状一致。

## 规则落在哪

- **规则文件的预算测试**：`≤ 8,000` 字节，每个 PR 的 CI 都跑。旁边另一条测试守着“必须保留的边界”那几条，删了就挂（第 9 篇讲过）。
- **全局规则只做路由**：具体流程写在对应技能里，全局规则只说“什么时候用哪个技能”。同一个数字只出现一次。

## 没解决的事

- **清理完 74 分钟，又涨回去 338 字节。** 21:35 清理合入，22:43 和 22:49 两次提交又加了 287 和 51 字节，现在 7,524，离新上限 476。按之前不到三天涨 873 字节的速度，估算两天左右就会再碰到上限。上限能挡住“超”，挡不住“满”。
- **冲突还是靠人查。** 字节数能测，两条规则互相矛盾测不出来。这次是我主动要求审一遍才发现的，下一处冲突什么时候出现、多久被发现，现在没有机制。

## 可以拿走的做法

1. **给常驻规则文件一个字节预算测试，上限定在现状下面。** 定在现状上面一点，就等于给了一块“还能加”的空间，它一定会被用完。
2. **按提交看余量，不要只看最后一次。** 下面这段只读 git 历史，列出每次改动后的大小、增量和余量。用 `sh` 跑。在我的仓库上跑，正好列出上面那张表的 4 行，以及清理之后的 3 行。

```sh
#!/bin/sh
# 用法：budget_log.sh <规则文件> <字节预算> [提交范围]；逐个改过该文件的提交，打印大小、增量、余量
file=$1; budget=$2; range=${3:-HEAD}
git log --reverse --format='%h %ad' --date=format:'%m-%d %H:%M' "$range" -- "$file" |
while read -r sha day time; do
  size=$(git cat-file -p "$sha:$file" 2>/dev/null | wc -c | tr -d ' ')
  [ -n "$prev" ] && delta=$((size - prev)) || delta=0
  printf '%s %s %s %6d B  %+5d  left %5d\n' "$day" "$time" "$sha" "$size" "$delta" $((budget - size))
  prev=$size
done
```

3. **加一条新规则时，先搜它的反面。** 新规则里的关键名词（比如“子代理”“续接”“会话”），在规则文件和所有技能里各搜一遍，看有没有哪句说的是相反的意思。我那条“不拿内置子代理顶替”，搜一下“子代理”就能看到技能第 4 步。
4. **同一件事只写一处，别的地方只链接。** 写两遍的细节，迟早有一遍是过时的。

这是系列第 11 篇。前面几篇一直在说“规则要放在 Agent 绕不开的地方”。这一篇说的是代价：每条绕不开的规则都要每个会话读一遍，放得越多，越容易互相打架。规则也需要预算，而且预算要比现状紧。
