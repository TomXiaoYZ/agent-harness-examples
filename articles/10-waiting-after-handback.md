# 子代理说“等通知”就交回了：21 张卡里 11 张提前交回，母会话一停就是 12 分钟

结论先说：**子代理一旦把等待放到后台、以“等通知”结束本轮，对母会话来说它就已经交卷了。** 11 月 21 日我在一个数据平台仓库里连续派了 23 张界面改进卡。能把子代理记录和回执时间对上的有 21 张，其中 11 张的验收子代理在 Codex 交回执之前就交回了。母会话收到的是一句“还在等”，然后它也停了，最长一次空等 12 分钟，直到我问了一句“怎么样了”。修法是一个提交：等待改成前台分段等，每段 170 秒，没等完就返回一个专门的退出码，让调用方原样再跑。

背景：我的分工是 Claude Code 拆卡、验收，Codex 写代码。每张卡由母会话派一个后台验收子代理，子代理负责起 Codex 终端、等回执、按清单复跑测试和浏览器检查，最后写判决。母会话只看判决，决定合不合。

## 发生了什么

那天上午的节奏很快，23 张卡从 10:52 派到 14:13（时间按 UTC）。问题出在“等回执”这一步。

当时的验收简报写的是：“用 Bash 后台运行 wait，等完成通知，不轮询。”子代理照做了：把 wait 放到后台，然后输出一句类似“派发已完成，正在等待 Codex 第 1 轮回执，后台通知到达后继续验收”的话，结束本轮。

对子代理自己来说，这没错，后台任务结束时它会被叫醒，接着验收。但对母会话来说，**子代理结束本轮就等于交回**。母会话收到一条“任务完成”的通知，内容却是半截报告。

两个具体的例子：

- **UX-3a**：子代理 11:36:53 交回，内容是“正在等待回执”。母会话 1 秒后回了一句“还在跑第 1 轮，还没有结果”，然后停下。回执 11:41:35 才写出来。中间是我 11:40 发了一条别的指令，母会话才重新动起来。
- **UX-10a**：子代理 13:59:05 交回，通知摘要写着它“在等自己的后台任务”。这次母会话连回复都没有，直接停了。回执 14:08:54 写出来，母会话没动。14:11:13 我问“怎么样了”，它才去查证据目录，发现回执早就到了。从提前交回到我开口，正好 12 分钟。

第二天凌晨我在另一个会话里说：“我发现母 agent 经常在空等，要么没有派发子 agent，要么子 agent 已经完成了。”

## 为什么会这样

翻会话记录，原因有三层。

**第一层：简报教子代理放后台。** 写简报的时候，我想的是“不轮询、省 token”，没想到子代理结束本轮对母会话意味着什么。

**第二层：前台也不能一直等。** 为什么不让子代理前台等两个小时？因为 Claude Code 会把跑超过 180 秒的前台命令自动转到后台，不管你设的超时是多少。所以前台等两小时这条路本来就走不通，子代理最后还是会变成“后台等 + 结束本轮”。

**第三层：通知会提前到。** 这一层是另一个子 agent 暴露的。11 月 21 日一个不向终端编排工具上报状态的子 agent，刚启动就被派发脚本报成了“本轮完成”。母会话相信了这条通知，去读结果，发现它还在跑，然后停下，之后没有任何东西会再叫醒它。同一类问题 11 月 19 日修过一次（子 agent 中途给母会话发消息，会让等待提前返回），这次是换了个入口又出现了。

三层叠在一起，结果都一样：**母会话以为有人会叫醒它，其实没有。**

## 修法：一个提交

11 月 22 日的修复（6 个文件，加 96 行、删 23 行）做了四件事：

1. **wait 改成前台分段等。** 每次最多等 170 秒，赶在 180 秒转后台之前返回。没等完就返回退出码 4，意思是“Codex 还在跑，原样再跑一次”。没结束就不写回执文件，免得半截结果被当成完整结果。
2. **别人发来的消息不再打断等待。** 母终端收到其他子 agent 的消息时，底层等待会提前返回。现在遇到这种返回就接着等，直到时间片用完。
3. **“本轮完成”要有证据才发。** 派发脚本记下发任务前子 agent 的轮次计数，计数前进了、状态也不是“工作中”，才通知母会话。不上报状态的子 agent，10 分钟后如实告诉母会话“判断不了，别空等它，自己去看”。
4. **全局规则加一句。** 母会话以“等结果”结束本轮之前，先确认有东西会叫醒它；子代理交回的是“还在等”而不是结果时，当场去证据目录核实，已完成就接着收，没完成就让它前台等到底。

## 规则落在哪

- **派发脚本的 wait 子命令**：默认时间片 170 秒，写成常量，旁边注释写着 180 秒这条限制。还在跑时返回 4，不写回执。
- **验收简报**：第二阶段第 2 步改成“前台运行 wait；退出码 4 就原样再跑；不要放后台、不要用 sleep 循环代替、不要以‘等通知’结束本轮”，并写明原因：子代理一交回，母会话就只拿到半截报告。
- **测试**：新增 3 条。一条验证“收到别人的消息不结束等待”，一条验证“还在跑时退出码是 4、不写回执”，一条断言默认时间片小于 180 秒。这个测试文件现在 9 条全过，修复那次的 CI 也是绿的。

## 没解决的事

- **修复合入还不到一天。** 我还没有修复后的派发数据，不能说空等已经消失了。下一批卡跑完，我会用同样的方法再数一遍“提前交回”的比例。
- **简报是文字，不是钩子。** 分段等让子代理没有理由再放后台，但如果它还是放了，没有任何机制拦住它。母会话那条“核实再停”的规则，是兜底。

## 可以拿走的做法

1. **看清楚“结束本轮”对上一层意味着什么。** 子代理里的“后台等、等通知”，在母会话眼里就是交卷。凡是要等的东西，等在交回之前，不要等在交回之后。
2. **工具会把长命令转后台，就把等待切成小段。** 下面这段是通用版：等一个回执文件，时间片用完返回 4，调用方看到 4 就原样再跑。我在本地试过两种情况：文件不出现，6 秒后返回 4；3 秒后文件出现，立刻返回 0。

```sh
#!/bin/sh
# 用法：slice_wait.sh <回执文件> [秒数]；回执出现返回 0，时间片用完返回 4（原样再跑）
receipt=$1; slice=${2:-170}
end=$(( $(date +%s) + slice ))
while [ "$(date +%s)" -lt "$end" ]; do
  [ -s "$receipt" ] && { echo "done: $receipt"; exit 0; }
  sleep 5
done
echo "still working: run the same command again"; exit 4
```

3. **数一数“提前交回”。** 对每张卡比较两个时间：子代理第一次交回的时间，和回执文件的修改时间。前者早于后者，就是提前交回。我那天是 21 张里 11 张，比例这么高，靠人盯是盯不过来的。
4. **“完成”通知要基于状态变化，不要基于时间。** 记下发任务前的轮次，轮次前进了才算这一轮结束。报不出状态的，就老实说报不出。

这是系列第 10 篇。前面几篇讲的是规则放在哪里 Agent 绕不开。这一篇讲的是另一面：等待也要放在绕不开的地方。等在交回之后，就等于没人在等。
